# v0.4.0 — Isolated-Session Handoff Spec

**Status:** Accepted
**Drafted:** 2026-05-08
**Tracking issue:** [#10](https://github.com/fruteroclub/intern-os/issues/10)
**Milestone:** v0.4.0
**Scope:** Add a deterministic, file-backed handoff layer to internOS so a coordinating agent can delegate to an isolated specialist session (subagent) without losing the active workstream binding, the minimum context, or the operational guardrails. Stays inside intern-os doctrine — no new framework.

---

## TL;DR

When a coordinator spawns an isolated specialist (Hermes `delegate_task`, OpenClaw `sessions_spawn`, Claude Code `Agent` tool, etc.), the specialist gets a fresh context with no inherited transcript or binding. internOS already says "files are the source of truth" — this spec extends that to multi-agent: the **handoff manifest** is a file in the workstream that points the specialist at exact files, exact paths, exact thread_id, and exact write-back targets. The specialist verifies the binding deterministically before doing anything, executes within explicit isolation rules, and writes its work to a designated artifact path. The coordinator owns the reconciliation back into `STATUS.md` / `BRIEF.md`.

Three-layer separation:

1. **Doctrine** — internOS rules (invariants below). Portable.
2. **Schema** — manifest format. Portable. Versioned (`internos_handoff: v1`).
3. **Adapter** — per-harness spawn mechanism (Hermes / OpenClaw / Claude Code / generic). Harness-specific.

---

## Doctrine — the four invariants

### 1. Deterministic resolution

The specialist verifies the binding before acting. Verification is exact-match only:

- `workstream_path` exists on disk
- `BRIEF.md` exists at `<workstream_path>/BRIEF.md`
- `BRIEF.md`'s `thread_id` field exactly equals the manifest's `thread_id`
- Every path in `load.required` exists

If any check fails: stop, return `aborted-binding-mismatch` with the failing check name. No fallback. No fuzzy matching. No "closest project."

### 2. Explicit isolation

The specialist loads only files in `load.required` (and optionally `load.optional` if the task warrants). It does not:

- read sibling workstreams
- broad-scan the workspace
- infer related files from naming proximity
- fall back to project-level reads not in the load list

Filesystem isolation is **doctrinal, not OS-enforced.** Each adapter section below documents what additional sandboxing each harness can provide on top.

### 3. Files are the source of truth

The manifest **points at** files. It does not embed their content. Specialists read `BRIEF.md` and `STATUS.md` from disk after verifying the binding, never from the manifest.

The specialist's output is also a file: the **return artifact** at `<workstream_path>/handoffs/<handoff_id>.md`. The free-text return to the coordinator is a one-line summary plus the artifact path, nothing load-bearing.

### 4. Role separation (writer scope)

Specialists are **confined to** these write paths:

- `<workstream_path>/handoffs/<handoff_id>.md` (the return artifact — required)
- `<workstream_path>/handoffs/<handoff_id>/*` (optional sub-artifacts when one file isn't enough)
- `<workstream_path>/MEMORY.md` (append-only, bounded — see schema)

Specialists **must not** write to:

- `BRIEF.md` (identity is coordinator-owned)
- `STATUS.md` (heartbeat is coordinator-owned)
- `DECISIONS.md` (decision log is coordinator-owned)
- Any file outside `<workstream_path>`

Reconciliation (updating `STATUS.md`, appending to `DECISIONS.md`) is the **coordinator's** job after reading the return artifact. This preserves the heartbeat invariant: at any point in time, `STATUS.md` reflects the coordinator's view of reality, not a specialist's intermediate state.

## Manifest schema v1

Canonical schema lives at `intern-os/schemas/handoff-v1.yaml` (added in this release). Manifests are YAML; JSON is acceptable where adapters require it.

```yaml
internos_handoff: v1                # schema version — required, enables forward compat
handoff_id: 2026-05-08-1430-research-amber  # unique, date-keyed; coordinator's choice
project: amber
workstream: market-validation
workstream_path: /Users/mel/workspace/projects/amber/workstreams/market-validation
thread_id: claude-code:projects/amber/workstreams/market-validation
role: market-research-specialist    # optional; descriptive only — the specialist's domain

load:
  required:
    - BRIEF.md
    - STATUS.md
  optional:
    - DECISIONS.md
    - docs/2026-04-22-discovery-call-acme.md

# Paths under load.required are resolved relative to workstream_path.
# Absolute paths are also accepted but discouraged — they break portability
# across machines.

task:
  objective: |
    Synthesize the market sizing implied by the discovery call notes.
    Identify the 3 most defensible wedges given current scope.
  success_condition: |
    Return artifact exists at write_back.artifact_path with sections
    "objective", "work", "findings", "open-questions" populated.
  stop_condition:
    - success condition met
    - blocked by a question only the human can answer (record it and stop)
    - any binding_check fails (return aborted-binding-mismatch)

binding_checks:                     # machine-testable, evaluated in order
  - workstream_path_exists
  - brief_md_exists
  - thread_id_matches
  - load_required_paths_exist

write_back:
  artifact_path: handoffs/2026-05-08-1430-research-amber.md
  artifact_schema:                  # required sections in the artifact, in order
    - objective
    - work
    - findings
    - open-questions
    - status                        # one of: done | blocked | aborted-binding-mismatch
  also_append:                      # optional, bounded
    - target: MEMORY.md
      max_lines: 5

isolation:                          # explicit, doctrinal — copied into specialist instructions
  - do not read sibling workstreams
  - do not modify files outside workstream_path
  - do not modify BRIEF.md, STATUS.md, or DECISIONS.md
```

**Field requirements:**

| Field | Required | Notes |
|---|:-:|---|
| `internos_handoff` | ✓ | schema version literal `v1` |
| `handoff_id` | ✓ | unique within workstream; date-prefixed convention recommended |
| `project`, `workstream`, `workstream_path`, `thread_id` | ✓ | identity; specialist verifies all four |
| `load.required` | ✓ | at minimum `BRIEF.md`, `STATUS.md` |
| `load.optional` | — | specialist reads only if task requires |
| `task.objective`, `task.success_condition`, `task.stop_condition` | ✓ | what / done-when / abort-when |
| `binding_checks` | ✓ | explicit array of named checks (extensible) |
| `write_back.artifact_path` | ✓ | always under `handoffs/` |
| `write_back.artifact_schema` | ✓ | enforces a stable return shape coordinator can parse |
| `write_back.also_append` | — | bounded MEMORY.md appends |
| `isolation` | — | redundant with doctrine but useful as inline reminder |
| `role` | — | descriptive |

## Storage convention

```
<workstream_path>/
├── BRIEF.md                                  ← unchanged
├── STATUS.md                                 ← unchanged
├── handoffs/                                 ← new in v0.4.0
│   ├── <handoff_id>.yml                      ← manifest (durable record)
│   ├── <handoff_id>.md                       ← return artifact (specialist output)
│   └── <handoff_id>/                         ← optional, for multi-file outputs
│       ├── intermediate-1.md
│       └── intermediate-2.md
└── ...
```

The `handoffs/` directory accumulates the audit trail: every delegation, what was asked, what was returned. Coordinator behavior is to keep manifests forever (cheap, useful for provenance); operators can archive old ones manually.

## Coordinator behavior

1. **Construct the manifest.** Choose a `handoff_id` (date-keyed). Fill all required fields. Pick a minimal `load.required` and `load.optional` — Tier 1 (`BRIEF.md` + `STATUS.md`) by default, escalate only when the task demands.
2. **Write the manifest** to `<workstream_path>/handoffs/<handoff_id>.yml`.
3. **Spawn the specialist** via the harness's native delegation primitive (see adapter sections). Pass the manifest path or content as the harness allows.
4. **Wait for completion.** Specialist returns `{artifact_path, status, summary}`.
5. **Read the return artifact** at `<workstream_path>/<artifact_path>`.
6. **Reconcile:**
   - If `status: done`, append to `DECISIONS.md` if appropriate, update `STATUS.md` to reflect new phase / next step / blockers.
   - If `status: blocked`, capture the blocker in `STATUS.md.blockers`, optionally surface to the human.
   - If `status: aborted-binding-mismatch`, **do not retry blindly.** Inspect the manifest for the failing binding check; this is a real bug somewhere (wrong thread_id, missing file, copy-paste error in the manifest). Fix and re-spawn.
7. **Optional: append handoff outcome to MEMORY.md** as one curated line for future-session context.

## Specialist behavior

The specialist's instructions (delivered by the coordinator via harness-specific transport) include the manifest plus this protocol:

```
1. Read the manifest at <manifest_path>.
2. Run binding_checks in order. If any fails, write the return artifact with
   status=aborted-binding-mismatch and the failing check name, then return.
3. Read load.required files. Optionally read load.optional if needed.
4. Execute the task.objective until either:
   - success_condition is observably true, or
   - a stop_condition fires.
5. Write the return artifact at write_back.artifact_path. Use the schema
   in write_back.artifact_schema. Set status field appropriately.
6. If write_back.also_append is set, append (do not overwrite) to the
   listed target(s), respecting max_lines.
7. Return to the coordinator: {artifact_path, status, one-line summary}.

Do not:
- read sibling workstreams
- modify BRIEF.md, STATUS.md, DECISIONS.md
- write outside <workstream_path>
- broad-scan the workspace
```

Specialists in trust-sensitive deployments may additionally be sandboxed (filesystem ACLs, container scoping). Doctrine alone is enforcement; sandboxing is defense-in-depth.

## Verification protocol (binding_checks)

Each `binding_checks` entry is a named, machine-testable predicate. v0.4.0 ships these named checks; adapters may add their own.

| Check | Predicate |
|---|---|
| `workstream_path_exists` | `os.path.isdir(workstream_path)` |
| `brief_md_exists` | `os.path.isfile(workstream_path + "/BRIEF.md")` |
| `thread_id_matches` | `BRIEF.md`'s `thread_id` field exactly equals manifest's `thread_id` (string equality, no normalization) |
| `load_required_paths_exist` | every path in `load.required` resolves and is readable |

Failure of any check → return artifact with `status: aborted-binding-mismatch`, body lists the failing check. No partial execution.

A reference shell implementation will ship at `intern-os/scripts/verify-handoff.sh <manifest-path>` in v0.4.0 — exits 0 on pass, exits 3 with a named failure on fail. Adapters may use it directly or reimplement in their host language.

## Per-harness adapter notes

### Hermes Agent

Native primitive: `delegate_task` spawns an isolated subagent with `goal` + `context` payload. No environment-variable inheritance for handoff data.

Adapter behavior:
- Coordinator writes manifest to `<workstream_path>/handoffs/<handoff_id>.yml`.
- Coordinator passes manifest **content** in `delegate_task.context` (not just the path — Hermes subagents may not have implicit filesystem access to the parent's cwd).
- Coordinator restricts subagent toolsets to file/terminal as needed.
- Subagent verifies via shell call to `verify-handoff.sh`.
- Output flows back via files + final summary message.

Hermes-specific manifest extensions (optional, ignored by other adapters):
```yaml
hermes:
  acp_command: ...        # if specialist runs through a specific ACP-capable agent binary
  acp_args: ...
  toolsets: [...]         # explicit allowlist for the subagent
```

### OpenClaw

Native primitive: `sessions_spawn` with `runtime="subagent"` and default isolated context (do not use `context: "fork"` — weakens isolation).

Adapter behavior:
- Coordinator writes manifest to `<workstream_path>/handoffs/<handoff_id>.yml`.
- Coordinator spawns isolated child with the manifest path as an attachment or in the `task` string.
- Subagent runs `verify-handoff.sh` as the first action; aborts on any failure.
- Subagent has workspace filesystem access by default — doctrine is the only protection against scope creep, so the manifest's `isolation` rules and tool allowlist do the work.

OpenClaw-specific notes:
- The child is not natively sandboxed to a single workstream subdirectory. For higher-trust scenarios, layer on filesystem ACLs or container scoping.
- Completion is push-based to the parent; transcript visibility is absent unless `fork` is used (don't).

### Claude Code

Native primitive: `Agent` tool (a.k.a. Task tool / subagent). Subagent gets a fresh conversation, inherits cwd + env vars, but no transcript or system prompt.

Important constraint: **`SessionStart` and `SessionEnd` hooks do not fire inside subagents.** Only `SubagentStop` does. The PR #16 lifecycle preload is unavailable for specialists. Therefore the manifest must be self-contained — every required field explicit — because there's no preload safety net.

Adapter behavior:
- Coordinator writes manifest to `<workstream_path>/handoffs/<handoff_id>.yml`.
- Coordinator constructs the subagent prompt as: a fenced YAML block containing the manifest, followed by the verify-then-execute protocol.
- Subagent runs `verify-handoff.sh` (or the equivalent in-prompt verification steps) before any task action.
- `SubagentStop` hook (configured globally in `~/.claude/settings.json`) can post-validate that the return artifact was written, log to a per-workstream audit file, etc.
- User-defined agent definitions at `~/.claude/agents/<name>.md` can codify the specialist protocol so the coordinator only has to provide the manifest.

### Generic / other harnesses

Treat the manifest file as the single source of truth. Coordinator writes the manifest; specialist reads the path; verification + execution + write-back follow the doctrine above. No adapter required if the harness can run a shell command — `verify-handoff.sh` is the portable verifier.

## Cross-protocol alignment

internOS is not the first system to formalize structured agent-to-agent handoff. Where this spec aligns with prior art:

- **A2A (Google) `Task` object** — id, role, parts, artifacts. The `internos_handoff` envelope maps cleanly: `handoff_id` ↔ task id, `role` ↔ role, manifest body ↔ parts, `write_back.artifact_path` ↔ artifacts. Future v0.4.x can ship an A2A serializer that emits the manifest in A2A-compatible JSON-RPC parts, no schema changes needed.
- **OpenAI Agents SDK `handoff`** — typed transfer-to with shared state. The intern-os version is doctrinally stricter (explicit load list, write-scope confinement, file-backed) but the conceptual primitive is the same.
- **MCP** — solves capability discovery and tool delegation. Does not standardize task delegation between agents. internOS handoffs sit *above* MCP: the manifest can declare which MCP servers the specialist needs, but the manifest itself is not an MCP message.
- **LangGraph / CrewAI / AutoGen** — pass structured state objects between graph nodes. Same shape, different transport.

What internOS does *not* invent:
- Transport (each harness has one)
- Identity scheme (uses existing `thread_id`)
- File format (YAML, machine-validatable)

What internOS *does* invent:
- Strict role separation (specialist write scope)
- File-backed manifest (durable audit trail by default)
- Verification protocol with named checks (extensible, machine-testable)

## Open questions — parked for v0.4.1+

These are real concerns that don't block v0.4.0 shipping. File as separate issues if and when they bite.

1. **Concurrent specialists.** What happens if a coordinator spawns two specialists for the same workstream simultaneously? Race condition on `MEMORY.md` appends? Do we need handoff-level locking or claim semantics? Out of scope for v0.4.0; likely resolved by convention (coordinators don't spawn parallel specialists for the same ws unless the task is genuinely independent).

2. **Reconciliation flow specifics.** This spec says "coordinator updates STATUS.md after reading the artifact." It does not specify *exactly how* — manual? Templated? Coordinator-side script? v0.4.0 leaves this as coordinator discretion.

3. **Manifest signing / trust.** For trust-sensitive deployments where a manifest could be tampered with between write and read, optional signing (e.g. detached signature file `<handoff_id>.yml.sig`). Out of scope for v0.4.0.

4. **Schema evolution path.** `internos_handoff: v1` is the current schema. v2 is allowed when needed; specialists should reject unknown schema versions rather than guess.

5. **Cross-workstream handoff.** Spec assumes the specialist works *within* a single workstream. What if the task genuinely spans two? Out of scope — the answer is "spawn two specialists, one per workstream," but if that becomes painful we'll spec it.

6. **Hooks-driven coordinator automation.** Could `SessionEnd` hook auto-reconcile artifacts written during the session? Probably yes for Claude Code adapter via PR #16's mechanism — defer until we see usage patterns.

## Notes for the implementer

- The reference verifier script is the single source of truth for what "verified" means. Adapters may inline their own checks but should match its semantics exactly.
- Treat the manifest as immutable once written. If the coordinator needs to amend, write a new manifest with a new `handoff_id` rather than editing in place — the audit trail wants this.
- Keep `verify-handoff.sh` POSIX. No bashisms beyond `[[`. It needs to run on whatever the specialist's environment is.
- The `binding_checks` array is **ordered**. Check `workstream_path_exists` first; without it, every other check is meaningless and will fail less informatively.
- When in doubt, prefer doctrine over harness magic. The spec is explicit so that any future harness can implement it without us redesigning.
